# INTEL-17: provenance and replay contract

**Date:** 2026-05-27
**Lane:** data excellence / provenance / replayability / trust
**Depends on:** INTEL-01 through INTEL-16
**Status:** canonical lineage contract for intelligence artifacts

## Why this exists

The intelligence layer will produce many derived objects:

```text
ANLZ phrase maps
section records
section vectors
transition candidates
smart-cue proposals
context packets
music claims
agent decisions
gold labels
scorecard reports
```

Each object already has some local metadata: source, confidence, content hash,
strategy version, model ID, or rubric version. That is necessary but not enough.

The app also needs to answer:

```text
Why did the pill suggest this track and cue?
Which exact section map, vector strategy, scorer weights, taste snapshot, and
context packet produced it?
Can we replay the decision later and get the same candidate slate?
If Kaan says it was wrong, which layer was wrong?
```

This spec defines the provenance/replay spine for those questions.

## External anchors

- W3C PROV defines provenance as information about entities, activities, and
  people involved in producing data, used to assess quality, reliability, and
  trustworthiness. It also explicitly covers reproducibility, versioning,
  procedures, and derivation.
  Sources: https://www.w3.org/TR/prov-overview/,
  https://www.w3.org/TR/prov-o/
- Model Cards recommend documenting model context, evaluation procedures, and
  performance characteristics.
  Source: https://arxiv.org/abs/1810.03993
- Datasheets for Datasets recommend documenting dataset motivation,
  composition, collection process, and recommended uses.
  Source: https://arxiv.org/abs/1803.09010

Applied here:

- We do not need full RDF/OWL in v1.
- We do need the core PROV shape: entity, activity, agent, and derivation.
- Every model/data/scorer swap needs a short machine-readable card.
- Every scorecard claim should be replayable from manifests.

## Vocabulary

### Entity

A data artifact:

```text
TrackIntelligence
SectionRecord
SectionVector
TransitionCandidate
SmartCueProposal
AgentContextEnvelope
MusicClaim
AgentDecision
GoldLabel
ScorecardReport
```

### Activity

A deterministic or bounded process that created an entity:

```text
anlz_parse
section_extract
section_embed
transition_score
smart_cue_place
context_compile
agent_decide
decision_validate
gold_label
scorecard_eval
```

### Agent

The actor or subsystem responsible:

```text
vibemix:<module>
model:<model_id>
human:kaan
tool:<tool_name>
```

Do not confuse this with an LLM agent. This is provenance vocabulary.

### Derivation

The explicit edge:

```text
entity B was generated by activity X using entity A
```

Example:

```text
TransitionCandidate tr_001
  wasGeneratedBy transition_score run transrun_20260527_001
  used SectionRecord rb-123#s010
  used SectionRecord rb-456#s002
  used SectionVector rb-123#s010/head
  used SectionVector rb-456#s002/head
  used TransitionScorerCard transition_scorer_v1
```

## Artifact identity rules

### `analysis_run_id`

One ID per offline intelligence build:

```text
analysis_run_id = "anrun_YYYYMMDD_HHMMSS_<short_hash>"
```

Generated when the app builds or refreshes section intelligence for a library.

### `representation_run_id`

One ID per representation/vector build:

```text
representation_run_id = "repr_YYYYMMDD_HHMMSS_<strategy>_<short_hash>"
```

Matches INTEL-14.

### `transition_run_id`

One ID per transition slate scoring batch:

```text
transition_run_id = "transrun_YYYYMMDD_HHMMSS_<strategy>_<short_hash>"
```

### `context_run_id`

One ID per context packet compile:

```text
context_run_id = "ctxrun_YYYYMMDD_HHMMSS_<short_hash>"
```

### `eval_run_id`

One ID per scorecard or benchmark run:

```text
eval_run_id = "eval_YYYYMMDD_HHMMSS_<suite>_<short_hash>"
```

Rules:

- run IDs are not action IDs;
- run IDs may appear in logs, reports, and private eval rows;
- public reports redact track IDs but can keep run IDs;
- run IDs must be deterministic enough for replay lookup, not for security.

## Provenance manifests

Use JSON for v1. Keep it boring and diffable.

Path:

```text
eval/private/intel/provenance/
  analysis_runs.jsonl
  representation_runs.jsonl
  transition_runs.jsonl
  context_runs.jsonl
  decision_traces.jsonl
  eval_runs.jsonl
  model_cards.jsonl
  dataset_cards.jsonl
```

Public/redacted reports may include aggregate excerpts under:

```text
.planning/eval/reports/
```

Never commit private provenance rows that contain local paths, raw track IDs, or
private notes unless explicitly redacted.

## Analysis run manifest

`analysis_runs.jsonl`

```json
{
  "analysis_run_id": "anrun_20260527_221500_a1b2c3d4",
  "created_at": "2026-05-27T22:15:00Z",
  "library_snapshot_id": "libsnap_20260527_ab12cd34",
  "track_count": 493,
  "anlz_root_hash": "sha256:...",
  "anlz_parser_version": "anlz_pssi_v1",
  "section_extraction_version": "section_extract_v1",
  "ontology_version": "ontology_v1",
  "source_priority": ["dj", "anlz", "auto", "fallback"],
  "coverage": {
    "tracks_with_sections": 449,
    "sections_total": 8531,
    "fallback_sections": 44,
    "parse_errors": 0
  },
  "warnings": []
}
```

Rules:

- `library_snapshot_id` should be derived from library metadata, not raw file
  paths.
- `anlz_root_hash` can hash relative ANLZ file names plus sizes/mtimes, not full
  local paths.
- coverage is part of provenance because missing data explains bad suggestions.

## Section record provenance

Each section record should be able to point back to:

```text
analysis_run_id
source
source_detail
source_confidence
role_mapper_version
section_extraction_version
content_hash
```

Add to `SectionRecord` metadata when implemented:

```python
analysis_run_id: str
role_mapper_version: str
section_extraction_version: str
```

If storage needs to stay compact, put these fields in `section_meta`, not in the
vector table.

## Agent decision provenance

When the LLM or deterministic template emits an `AgentDecision`, preserve:

```text
decision_id
context_run_id
packet_id
claim_ledger_hash        # INTEL-21: typed claims available to this decision
model_router_decision_id?   # if available
agent_backend
agent_model_alias           # not hardcoded model name in product logic
validator_version
validator_result
fallback_action
decision_source             # INTEL-20: deterministic/model_validated/degraded/etc.
gate_results_hash
latency_breakdown_ms
```

Rules:

- store prompt/output only in debug/replay mode, not by default;
- normal provenance stores structured decision fields, not full transcripts;
- validator rejects are first-class evidence, not logs to ignore.
- INTEL-20 `AgentDecisionTrace` is the richer private replay row; this manifest
  stores the compact provenance pointer and aggregate-safe fields.

## Gold-label provenance

INTEL-15 labels should carry:

```text
review_session_id
label_id
rubric_version
analysis_run_id?
representation_run_id?
transition_run_id?
context_run_id?
lineage_status
split
```

Rules:

- if a label judges a transition, include `transition_run_id`;
- if a label judges representation retrieval, include `representation_run_id`;
- if a label judges live pill timing, include `context_run_id`;
- if a label cannot be traced to a run, mark `lineage_status="partial"` and do
  not use it for release claims.

## Replay guarantees

### Tier 0: audit replay

Can reconstruct:

- which inputs and versions produced a report;
- coverage and counts;
- IDs of objects involved.

No guarantee of byte-identical candidate ranking.

### Tier 1: deterministic replay

Can rerun:

- section extraction from the same library/ANLZ snapshot;
- section vector lookup from the same representation run;
- transition scoring with the same weights;
- context compile with the same packet inputs.

Expected:

- same candidate IDs and ordering;
- same score components within deterministic float tolerance;
- same validator outcome.

### Tier 2: model-output replay

Can rerun or inspect:

- exact context packet;
- exact model output if debug capture was enabled;
- validator decision.

Not required by default because transcript capture has privacy cost.

Product target:

```text
Tier 1 for scorecards.
Tier 0 for normal user sessions.
Tier 2 only for explicit debug/eval runs.
```

## Privacy rules

Private provenance may contain:

- run IDs;
- track IDs;
- section IDs;
- candidate IDs;
- timestamps;
- score components;
- model/strategy versions.

Private provenance must not contain by default:

- raw local paths;
- raw audio;
- private recordings;
- full LLM prompts/responses;
- unredacted free-form notes;
- API keys or secrets.

Public reports may contain:

- run IDs;
- aggregate metrics;
- redacted/hashed track IDs;
- role/source/count summaries;
- model family and strategy version.

Public reports must not contain:

- unredacted local track IDs if they identify private library content;
- local paths;
- notes that mention private tracks unless manually reviewed.

## Validation rules

`intel_provenance_report validate` should fail on:

- unknown run ID reference;
- missing strategy/model/rubric version;
- local path in public report;
- label used for release claim with `lineage_status="partial"`;
- eval report without threshold lock version;
- context run without schema version;
- transition candidate without `transition_run_id`;
- representation run without model card ID;
- section record without `analysis_run_id`.

## How this helps debugging

When a suggestion is wrong, classify the failure:

```text
source failure:
  ANLZ/section boundary or role wrong
representation failure:
  section similarity retrieved the wrong feel
scorer failure:
  weights/risk policy ranked a bad candidate high
context failure:
  compiler exposed the wrong or too much context
agent failure:
  model selected/explained poorly inside valid context
validator failure:
  invalid decision slipped through
taste failure:
  learned preference overrode too much or came from bad labels
live failure:
  timing/playhead confidence was wrong
```

Every one of those maps to a run manifest. That is how the app improves without
superstition.

## Build order

Do not implement this before PR 1. Add it when the first section store exists.

Recommended sequence:

1. Add `analysis_run_id` to section extraction outputs.
2. Add `representation_run_id` to section vector builds.
3. Add `transition_run_id` to transition candidates.
4. Add `context_run_id` to context compiler outputs.
5. Add provenance refs to gold labels.
6. Add `eval_run_id` to scorecard reports.
7. Add redacted provenance report command.

## Success definition

The provenance layer is good enough when:

```text
every section can explain its source and analysis run;
every vector can explain its model/strategy/window policy;
every transition candidate can explain its scorer/weights/run;
every context packet can explain its candidate slate and confidence policy;
every gold label can point at the thing it judged;
every scorecard report can be replayed or marked non-replayable;
public reports redact private identifiers;
debugging a bad suggestion identifies the failing layer.
```

This is the trust layer under the musical brain. Without it, the app can be
impressive. With it, the app can become excellent.
