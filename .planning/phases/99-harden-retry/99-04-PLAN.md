<objective>
Land the cross-process propagation seam: a side-channel file (`VIBEMIX_STOP_REASON_FILE` env var → temp path) that the MCP subprocess's `LibraryToolset` writes on threshold-trip and the parent-process wrapper (`curate_with_codex` / `build_set_with_codex`) reads after Codex exits. The wrapper translates the dict payload into `CodexCurateResult(stop_reason="tool_starvation", error=<hint>)` / `CodexBuildSetResult(stop_reason="tool_starvation", error=<hint>)`.

Plus the B1 env-var passthrough probe: a startup log line in `library/mcp_server.py::build_toolset()` records whether `VIBEMIX_STOP_REASON_FILE` reached the MCP subprocess (the second of two process boundaries: wrapper → Codex CLI subprocess → MCP server child). If Codex CLI strips env vars when spawning MCP children (sandbox / hygiene), the toolset's write silently no-ops and starvation never propagates — but the acid test in Plan 99-08 catches this BEFORE Kaan's real Codex run via Plan 99-08's §HARDEN-PHASE-A-ENV-PROPAGATION-VERIFY checkpoint.

Purpose: Bridge the in-process toolset signal (Plan 99-03) to the wrapper-level result API so CLI / Telegram / GUI callers see a uniform `stop_reason`. This is the load-bearing architectural seam — it bypasses the LLM entirely (Channel A in RESEARCH.md § Stop-Reason Propagation Channel). The startup log makes the second-boundary passthrough an observable invariant, not an assumption.

Output: `_write_side_channel(payload)` method on `LibraryToolset`; `VIBEMIX_STOP_REASON_FILE` allocation + env-var injection + post-`_runner` read in BOTH `curate_with_codex` and `build_set_with_codex` (located at `codex_curate.py:382` and `codex_curate.py:672` per RESEARCH.md); one startup log line in `mcp_server.py::build_toolset()`; four propagation tests in a new `tests/library/test_codex_curate_stop_reason.py` file; two side-channel tests in the existing starvation test file.

<antipatterns_to_avoid>
- Reading the side-channel file OUTSIDE the `with tempfile.TemporaryDirectory(...)` block — the temp dir is cleaned up at the `with` exit; the file disappears with it (Pitfall 4 — "Side-channel file written but never read").
- Writing the file before allocating it — the wrapper allocates the path inside `tempfile.TemporaryDirectory`; the MCP subprocess inherits the env var via `subprocess.run(..., env=env)`. If the env var is set on `os.environ` directly (not the subprocess env arg), test isolation breaks.
- Letting `json.JSONDecodeError` / `OSError` bubble up — wrapper's read MUST be wrapped in `try/except (OSError, json.JSONDecodeError): pass` so a malformed file gracefully falls through to the existing parse logic (T-99-07 mitigation).
- Hardcoding `"tool_starvation"` in the wrapper's check IF that prevents Phase 100 from adding a sibling — the wrapper must branch on `payload.get("reason")` so Phase 100 can extend with `elif payload.get("reason") == "clarification_needed":` cleanly.
- Forgetting that `_runner_writing` helper (`tests/library/test_codex_curate.py:61`) ONLY writes `out.json`. The propagation tests need a NEW or EXTENDED helper that ALSO writes `stop_reason.json` to the temp dir. Do NOT modify `_runner_writing` in place — clone or extend so existing `test_codex_curate.py` tests stay green.
- Allocating the side-channel file via `tempfile.mkstemp` outside the `TemporaryDirectory` context — that creates a file outside the auto-cleaned directory, leaking files across runs (T-99-06).
- Polite-AI fallback hedging in the wrapper-side fallback string — the W3 fix replaces `"Viber ran out of grounded options."` with `"no playlist — tool starvation, no hint available"` AND notes the fallback is unreachable in production (Plan 99-03's case dispatch always populates `hint`). Mirrors the Telegram bridge fix in Plan 99-07.
- Logging the env-var VALUE in the mcp_server startup line WITHOUT recognizing it's a temp-dir path (`/var/folders/.../T/viber-codex-XXXX/stop_reason.json` on macOS). The path itself is user-owned, not a secret — log it verbatim. The privacy rule (CLAUDE.md) covers user transcripts/sessions, NOT temp-dir paths.
- Putting the startup log AFTER `load_dotenv()` — `.env` does not set `VIBEMIX_STOP_REASON_FILE` (the wrapper sets it on the subprocess env arg, not the parent's `.env`). Placement before or after dotenv is equivalent for the value, BUT placing it FIRST gives the cleanest stderr log ordering — the env-var probe is the first thing the MCP boot says.
</antipatterns_to_avoid>
