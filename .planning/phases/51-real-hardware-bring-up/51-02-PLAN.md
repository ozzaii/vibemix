<objective>
Fix the stale-sidecar dev loop surfaced live this session: `cargo tauri dev` runs a PRE-BUILT PyInstaller binary (`tauri/src-tauri/binaries/vibemix-core-<triple>/...`, resolved via `resource_dir()`), so `src/vibemix/` edits — e.g. the Phase-52 BPM stabilizer `fd25337` — are invisible until a full rebuild. Add an env-gated dev path that spawns the sidecar from repo source so live testing reflects HEAD, keep the bundled/release path byte-for-byte unchanged when the flag is absent, and ship a one-command rebuild route + dev-loop doc.

Purpose: bring-up triage (BRINGUP-04) is impossible if your fixes don't show up when you run the app. This makes "what I edit is what I test" the default dev experience without any risk to the shipped binary.

Output: an env-gated source-spawn branch in `sidecar.rs` (+ Rust unit test), `scripts/dev/run_sidecar_from_source.sh`, and `docs/dev-loop.md`.
</objective>

`spawn_sidecar_with_watchdog(app, wizard_mode, log_path)` (sidecar.rs:80) loops:
  - sidecar.rs:104 `let sidecar_bin = resolve_sidecar_path(&app)...` — resolves the BUNDLED binary via `app.path().resource_dir()` → `binaries/vibemix-core-<triple>/vibemix-core-<triple>`.

  - Exit-code sentinels: 0 = clean (with wizard→session handoff at :172), 2 = port-in-use, 3 = audio-device-missing (sidecar.rs:190-210). These MUST be preserved verbatim in the dev path.

`resolve_sidecar_path(app)` (sidecar.rs:248) — calls `resource_dir()`; under `cargo tauri dev` this points at the dev resource dir which may not contain a freshly-rebuilt onedir. It is the wrong source of truth for a live-HEAD dev loop.

The real cohost entrypoint is the FLAG-LESS `python -m vibemix` (`src/vibemix/__main__.py::main()`) — same branch the bundled binary runs. `--wizard` selects the wizard branch. So the dev source spawn = `<python> -m vibemix [--wizard]` with the repo root as cwd and `src` on PYTHONPATH (or `uv run`, which resolves the project automatically).

`build_sidecar.py` (scripts/) runs PyInstaller → `dist/vibemix-core/` onedir → copies into `tauri/src-tauri/binaries/vibemix-core-<triple>/` via `install_into_tauri_binaries`. This is the canonical rebuild route for prod. It is slow (full PyInstaller); the dev source-spawn avoids it.

Rust test scaffold already exists: sidecar.rs `#[cfg(test)] mod tests` (sidecar.rs:295) with `tempfile` + `read_last_log_line` coverage — extend it.

<dev_spawn_decision>
<!-- RESEARCH §2 decision: Opt C, A-first. -->
- Gate on env var `VIBEMIX_DEV_SIDECAR=1` (read via `std::env::var`). When set, the spawn builds the command from a Python interpreter + `-m vibemix` against the repo root, NOT via resolve_sidecar_path()/resource_dir().
- Branch BEFORE the `resolve_sidecar_path(&app)` call so the dev path never touches resource_dir().
- Interpreter resolution order (dev path): honor `VIBEMIX_DEV_PYTHON` if set (explicit override), else default to `uv run python` (project venv auto-resolved). The repo root is derived from a `VIBEMIX_DEV_REPO` env (set by run_sidecar_from_source.sh / a dev launch) or `CARGO_MANIFEST_DIR`'s parent — choose the deterministic one and document it.
- Release builds: when the flag is absent the code path is identical to today's (resolve_sidecar_path → shell().command(bin) → optional --wizard). No behavioral change, provable by the unit test.
</dev_spawn_decision>
