# vibemix — Zero-Config Ship-Blocker Map (2026-05-30)

> Source: workflow `zero-config-audit` (run wf_bff20cce-f0e, 15 agents, 1.19M tokens).
> 4 parallel auditors (env-vars / wizard-coverage / first-run-friction / hardcoded-assumptions)
> -> synthesis -> adversarial verify. Goal bar (Kaan): **install -> wizard -> works. Nothing else.**

## The honest read

Honest read: the app is NOT close to "install → wizard → works" — it is several ship-blockers away, and they cluster into two fatal classes that hit essentially every real first-run. (1) The co-host has no way to authenticate: shipped default mode is 'direct' (config_store.py:192, __main__.py:708), which demands a GEMINI_API_KEY that no wizard/Settings/Tauri path ever collects, so a fresh user hits sys.exit(4) and the co-host never speaks. The keyless Bravoh proxy path exists and is zero-config, but its default-flip is parked as KAAN-ACTION pending live endpoints (__main__.py:699-702). (2) Audio capture hard-asserts 48000 Hz on both macOS (open_capture, _audio_macos.py:647) and Windows (assert_wasapi_loopback_rate, _audio_windows.py:98) — but factory-default BlackHole and most Windows speakers are 44.1k, so the runtime crashes uncaught the moment a track plays; the fix pattern (native-rate open + resample) already exists in the same file for the output path but was never applied to capture, and the callback resampler also hardcodes 48k so even a partial fix would mis-ground every event. On top of that, the entire one-click install chain (BlackHole install, 48k format-check, driver-fetch) was BUILT as wizard components but never wired into STEP_ORDER (router.ts:168), the one 'Fix it' button is a no-op stub that lies about success (audio_config.py:209), and the wizard completes + locks first_run_completed without ever validating the capture path or offering a re-run. Two shipped features (memory recall, library/CLAP) are also dark or terminal-only. The good news: every gap has a concrete, mostly-already-written fix; the bad news is the headline two are gated on Kaan decisions (proxy default + the native-rate audio refactor), and until those land no real DJ reaches a working co-host.

## Prioritized findings

### [SHIP_BLOCKER] No GEMINI_API_KEY anywhere on a fresh install → sys.exit(4), co-host never speaks (the headline ship-blocker)
- **Where:** `src/vibemix/__main__.py:708 (mode default 'direct') + :724-735 (exit 4) + runtime/config_store.py:192 (llm_mode='direct')`
- **Verdict:** must_default_on
- **Fix:** Flip the shipped default from 'direct' to 'proxy' (the flip is already parked in-code as KAAN-ACTION at __main__.py:699-702, gated on Bravoh /register+/health+/v1 being live). Proxy mode self-provisions: it auto-mints install_uuid+JWT against https://api.altidus.world (default already set, __main__.py:711) and needs ZERO user key. Until the proxy endpoints are confirmed live, the wizard MUST gain an API-key step that writes the key to keyring (the `keyring` dep is already pinned) or app_data_dir()/.env (the path _load_env_robust already probes). Today there is NO wizard step, NO Settings field, NO Tauri command that ever collects a key — grep of tauri/ui/src/wizard + settings returns nothing; the only mention is crash-banner.ts telling the user to hand-edit a dotfile.
- **Why it matters:** A real DJ installs, sails through the wizard, hits play, and the co-host instantly dies — the single thing the product exists to do never happens, and there is no in-app way to fix it.

### [SHIP_BLOCKER] open_capture hard-asserts 48000 Hz on the master input → SampleRateMismatchError crashes main() on a default 44.1k BlackHole
- **Where:** `src/vibemix/platform/_audio_macos.py:647 (assert_device_sample_rate) called from __main__.py:2247 with sample_rate=INPUT_SR_NATIVE=48000 (audio/constants.py:21), NO try/except at the call site`
- **Verdict:** auto_detect
- **Fix:** Make open_capture open the input at the device's NATIVE rate and resample internally — the exact pattern already lives 20 lines down in open_passthrough_output (_audio_macos.py:686-689 reads info['default_samplerate'] and resamples). Read device_sr = int(sd.query_devices(idx)['default_samplerate']), open at that rate, resample device_sr→16k in the callback (resample_audio already exists). Drop assert_device_sample_rate from the capture path to a non-fatal warning. The auto-fix path (set_device_nominal_sample_rate via a `swift -` subprocess) requires Xcode Command Line Tools that are ABSENT on a fresh consumer Mac, so it routinely fails.
- **Why it matters:** A freshly-installed BlackHole 2ch is 44.1 kHz by factory default — so the most common real first-run boots straight into a Python traceback the moment the DJ plays a track, and the app looks bricked.

### [SHIP_BLOCKER] Callback resampling hardcodes source_sr=48000 — even after a native-rate open, events would ground on subtly-wrong audio
- **Where:** `src/vibemix/__main__.py:471/497/502 (resample_audio + deck process all pass INPUT_SR_NATIVE)`
- **Verdict:** auto_detect
- **Fix:** Thread the real capture rate (from sd.query_devices(input_idx)['default_samplerate'], the value open_capture should adopt) into _input_callback_factory as a captured constant and use it as source_sr everywhere instead of the module-level INPUT_SR_NATIVE. This must land WITH the open_capture native-rate fix — fixing one without the other turns a crash into silent miscalibration (~8.8% tempo/pitch error reading 44.1k as 48k), which is worse: the AI would 'work' but react to wrong BPM/phrase/drop detection.
- **Why it matters:** The whole anti-slop thesis is 'react to real detected events' — feeding the detectors mis-rated audio makes every BPM/drop/phrase call subtly wrong, which is exactly the fake-feeling reaction Kaan said would kill the product.

### [SHIP_BLOCKER] Windows WASAPI loopback capture hard-fails unless default format is exactly 48000 Hz
- **Where:** `src/vibemix/platform/_audio_windows.py:98-107 (assert_wasapi_loopback_rate raises) called from open_capture:234`
- **Verdict:** auto_detect
- **Fix:** Open the WASAPI loopback stream at the device's reported defaultSampleRate (the function already reads it into `actual` at line 95 — use it instead of rejecting it) and resample defaultSampleRate→16k for analysis, mirroring the macOS open_capture fix. Do not require 48000.
- **Why it matters:** Windows 'Speakers' very commonly default to 44.1 kHz/16-bit, so this likely breaks the majority of Windows first-runs with a crash that tells the user to dig through Control Panel → Sound → Advanced — the exact OS fiddling the zero-config bar forbids.

### [SHIP_BLOCKER] BlackHole not installed → sys.exit(3); the wizard detects but never actually installs or verifies routing
- **Where:** `src/vibemix/__main__.py:1016-1032 (exit 3) + audio/device_select.py:160 (MasterCaptureNotFoundError); wizard only probes (wizard.py:249)`
- **Verdict:** wizard_should_set
- **Fix:** Make the wizard's driver-fetch step a hard, verified gate: bundle the BlackHole .pkg in the DMG/Inno, run it from the wizard, then confirm the device enumerates AND that real signal (RMS > floor) is arriving before Continue arms — with inline 'route your DJ app master to BlackHole' guidance, since the wizard today never checks the DJ app is actually routed. The VIBEMIX_AUTO_MASTER_INPUT=1 sidecar default does not help: auto-master still raises the same not-found error when no loopback exists.
- **Why it matters:** Audio capture is everything; a user with no BlackHole (or who skipped the install/reboot/approval) boots into an exit-3 banner telling them to run `brew install` — a terminal step no real DJ will do.

### [HIGH] Wizard completes unconditionally and never re-runs — a broken/missing/44.1k capture path gets locked in permanently
- **Where:** `src/vibemix/runtime/wizard.py:422-434 (_on_wizard_done just logs+stops, no input-capture validation) + tauri/src-tauri/src/config.rs:150 (is_first_run gates --wizard on first_run_completed)`
- **Verdict:** wizard_should_set
- **Fix:** Gate _on_wizard_done (and the Rust first_run_completed write) on a real input-capture readiness check: BlackHole present AND a successful test open of the capture stream at the rate the runtime will actually use. The wizard's current audio probe only checks the OUTPUT device rate — it never opens the BlackHole INPUT that actually crashes. Also expose a 'Re-run setup' entry so a stuck user can recover instead of being permanently locked into a crashing config.
- **Why it matters:** Right now a user can pass the wizard with no working capture path and have no door back into setup — the one promise of 'wizard → it works' is unenforced.

### [HIGH] Orphaned install-chain wizard steps (forewarning / driver-fetch / format-check / blackhole) declared but never rendered — the zero-touch install was built and never wired in
- **Where:** `tauri/ui/src/wizard/router.ts:59-61 (types declared) — absent from STEP_ORDER:168-176 (only permissions/audio/controller/skill-level/profile-consent/telemetry-consent/smoke-test) and from both render switches`
- **Verdict:** wizard_should_set
- **Fix:** Finish plan-49-04: add forewarning/driver-fetch/format-check to STEP_ORDER and the render switch, tie driver-fetch to the bundled BlackHole installer and format-check to the 48k probe. The components (step-forewarning.ts, step-driver-fetch.ts, step-48k-probe.ts, blackhole-step.ts) already exist — they are dead code today.
- **Why it matters:** The exact steps engineered to make install zero-touch — driver fetch, format check, BlackHole setup — ship disconnected, so every gap above lands on the user instead of the wizard.

### [HIGH] Wizard's 'Fix it' button for the 44.1k→48k rate is a no-op stub that reports success
- **Where:** `installer/companion/audio_config.py:209-219 (configure_routing_darwin only does sentinel.touch() + returns ok:True) wired via tauri/ui/src/wizard/step-48k-probe.ts:136`
- **Verdict:** must_default_on
- **Fix:** Best path: make this moot by landing the native-rate-accept fix (open_capture finding) so the 48k probe becomes advisory, not load-bearing. If a real fix is kept, configure_routing_darwin must actually set kAudioDevicePropertyNominalSampleRate=48000 on BlackHole (reuse set_device_nominal_sample_rate, _audio_macos.py:103) and verify via re-probe — not touch a flag and claim success.
- **Why it matters:** A user who DOES hit the rate problem clicks the one repair button the app offers, it says 'fixed', the re-probe still fails, and they later crash anyway — a worse betrayal than no button at all.

### [HIGH] 48kHz format check probed but never gated; the Audio MIDI Setup step is orphaned (also: wizard FAILS any non-48k output that actually works)
- **Where:** `src/vibemix/runtime/wizard.py:302 (programmatic_pass = actual_rate == 48000) + tauri/ui/src/wizard/step-48k-probe.ts (dead, not in STEP_ORDER)`
- **Verdict:** wizard_should_set
- **Fix:** Drop the strict actual_rate==48000 equality as a pass condition — open_voice_output and open_passthrough_output already resample 44.1k cleanly at runtime, so the wizard currently FAILS devices that work fine (headphones, audio interfaces, default Windows speakers). Treat any device the OS can open as a pass, and generate/play the calibration tone at the device's default_samplerate (already read into actual_rate), not a hardcoded 48000. Wire step-48k-probe into STEP_ORDER only as advisory guidance once the capture-side native-rate fix lands.
- **Why it matters:** A DJ on perfectly good headphones or an external interface gets told their working audio gear 'failed calibration' and is sent to fiddle in Audio MIDI Setup for no reason.

### [HIGH] Master-input + mic device never persisted from the wizard — name-based resolution drifts and silently breaks
- **Where:** `tauri/src-tauri/src/config.rs:64-71 (FirstRunState stores only output_device_id) + src/vibemix/agent/config.py:56,58 (INPUT/MIC resolved by literal name each boot)`

- **Why it matters:** A DJ on a Mac mini/Studio, with a USB mic, multiple BlackHole variants, or non-English macOS gets no wizard control and a config that breaks on the next plug/unplug or reboot.

### [MEDIUM] open_mic_capture also hard-asserts 48000 — a 44.1k mic is silently disabled, killing talk-back with no reason shown

- **Why it matters:** Any 44.1k input mic (common on USB/interface rigs) silently removes the DJ's ability to talk to the co-host, with no error and no clue why.

### [MEDIUM] Viber's Codex backend requires an external `codex` install + login with no in-app prompt

- **Why it matters:** A DJ who opens Viber set-prep without Codex installed gets nothing, with no explanation of the one external step needed to make it work.

### [LOW] Output device persisted by positional index, not stable UID — can route the AI voice to the wrong device after a hardware change
- **Where:** `src/vibemix/audio/device_select.py:246 (output_device_id is a positional query_devices() index)`
- **Verdict:** auto_detect
- **Fix:** Persist the output by stable CoreAudio UID / name and resolve by UID at boot, keeping the existing graceful fallback chain (preferred index → name → OS default → first non-loopback) as backup. Low priority versus the crash findings since it degrades to OS default rather than crashing.
- **Why it matters:** After plugging in headphones or rebooting, a stale index can send the AI's voice to the wrong output and the DJ just hears silence with no error.
